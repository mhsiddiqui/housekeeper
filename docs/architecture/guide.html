Housekeeper architecture

How the code is put together, why it is built from small parts instead of a class hierarchy, and exactly what it takes to support a distribution (or an operating system) that Housekeeper does not support today.

1. The goal

Linux software arrives from many places: the distribution's package manager (apt, dnf, zypper, pacman…), app formats (Flatpak, Snap, AppImage), language tools (npm, pipx, uv, pip, cargo) and plain scripts. Distributions differ mostly in one of these, the native package manager. Everything else is the same everywhere.

So the design keeps every "way software gets installed" as its own small, independent part, and lets each distribution be described as a list of parts. A new distribution is a new list, sometimes with one new part. Nothing that already works has to change.

2. The whole picture

coreKnows no operating system

Defines what a package is, what a source must be able to do, and services like "scan everything in parallel". It never mentions dpkg, Flatpak or Linux, and it builds on any operating system.

linuxKnows Linux

One small type per way software gets installed on Linux, plus LinuxPlatform, which detects the distribution and picks the right ones.

platformKnows which OS crate

One function, detect, returns the platform for the OS Housekeeper was built for, or an Unsupported error. It is the only crate that depends on the OS crates (decision D27).

front endKnows people

Turns a scan into a table, JSON or (later) a window. It calls housekeeper_platform::detect and talks to core from then on.

3. Composition, not inheritance

A class-hierarchy design would look like PackageManager → AptManager → UbuntuManager, with every subclass inheriting (and overriding) a long list of methods. Two things go wrong with that for Housekeeper:

  • Distributions are mixtures, not specialisations. Ubuntu is "dpkg + Snap + Flatpak + npm + …". Fedora is "rpm + Flatpak + npm + …". There is no sensible parent class; there is a set of parts.
  • Abilities differ per part. Flatpak can remove an app; an AppImage has no uninstaller at all. A base class would force every part to implement (or fake) every ability.

Rust has no class inheritance anyway. Instead, Housekeeper uses three ideas:

IdeaIn Housekeeper
Program to an interface (a trait)Code that scans only knows dyn Source, never DpkgSource.
Has-a instead of is-aA platform has a list of sources; the app has a platform and a host; a host has a command runner.
Small, separate interfaces"Can list packages" is one trait. "Can remove", "can install a file", "can update" will each be their own trait, offered only by the sources that can.

4. The parts

Source: one way software gets installed

pub trait Source: Send + Sync {
    fn info(&self) -> SourceInfo;                                   // id "dpkg", label, kind (system, universal…)
    fn probe(&self, host: &Host) -> Availability;                 // cheap: is it on this machine?
    fn inventory(&self, host: &Host, scan: &ScanContext) -> Result<Vec<Package>, SourceError>; // everything it installed
    fn owner_lookup(&self) -> Option<&dyn OwnerLookup> { None }    // optional ability (section 7)
    fn file_list(&self) -> Option<&dyn FileList> { None }          // optional: the files one package installed
    fn dependant_lookup(&self) -> Option<&dyn Dependants> { None } // optional: what needs one package
    fn remover(&self) -> Option<&dyn Remover> { None }            // optional: how one package is removed (a plan)
    fn install_roots(&self, host: &Host) -> Vec<PathBuf> { vec![] }  // where its programs live
}

A source never holds another source. While it is read, its ScanContext gives it every source of the platform and a place to report warnings (decision D23). Only the manual source uses it today: it leaves out paths a native source's owner_lookup() owns and programs that resolve into another source's install_roots(), so a new source never shows up twice.

Thirteen sources exist today. Each one is a single file that knows one format:

KindSourcesHow each reads the machine
System (native)dpkg, rpm, pacmandpkg-query --showformat, rpm --queryformat, pacman's database files
Universalflatpak, homebrew, snapflatpak list --columns, Homebrew's Cellar/Caskroom and install receipts, snapd's REST API on its socket
PortableappimageFile magic bytes in the usual folders
Languagenpm, pipx, uv, pip, cargoTheir own metadata files (no interpreters started)
Manualmanual/opt, ~/.local/bin, symlink farms, known script installers

Platform: one operating system

pub trait Platform: Send + Sync {
    fn system(&self) -> &SystemInfo;            // "Ubuntu 26.04", family "debian", image_based…
    fn sources(&self) -> &[Arc<dyn Source>];    // the parts that apply to this system (shared, see section 5)
    fn launchers(&self, host, scan) -> Vec<Launcher>; // the application menu (desktop entries on Linux); default: none
    fn metainfo(&self, host, scan) -> Vec<Metainfo>;  // app catalog entries (AppStream on Linux); default: none
    fn command_dirs(&self, host) -> Vec<PathBuf>;     // where commands live; default: the PATH
}

After the sources are read, the scan attaches every launcher, every catalog entry, and every command a package database lists, to its package with the same evidence housekeeper who uses (decision D28). That is how a .deb with a menu entry becomes an app with a title and an icon, and a package with neither a command nor a launcher (fonts, firmware, data) becomes a component the default list hides. Then it groups the apps installed more than once by the AppStream IDs, launcher IDs, names and commands they share (D29), without merging them.

Host: the machine, seen through one door

Sources never call std::fs or start programs directly. They ask the Host:

host.read_to_string("/var/lib/dpkg/status")   // paths are "logical"; the host maps them under its root
host.home()                                  // the user's home
host.run_ok(&Cmd::new("rpm").arg("-qa"))       // goes to the CommandRunner it was given

The host is itself composed: a root directory, a home, environment variables, and a CommandRunner (argv only, never a shell, always a timeout). Swap the runner and the same sources run against recorded output in tests.

Housekeeper: the composition root

let host = Host::local();
let platform = housekeeper_platform::detect(&host)?;  // LinuxPlatform on Linux: the parts for this distro
let housekeeper = Housekeeper::new(platform, host);
let scan = housekeeper.scan(&Selection::All);          // every source, in parallel

5. How the parts are assembled

This is the real assembly code in crates/platform/linux/src/lib.rs, shortened. It never names a source:

let distro = Distro::detect(host);                                    // reads /etc/os-release
let native = native_provider(&distro, host, PROVIDERS);          // DpkgSource, "debian" on Ubuntu
let context = Context { distro: &distro };
let mut sources: Vec<Arc<dyn Source>> = native.map(|(p, _)| p).into_iter()
    .chain(PROVIDERS.iter().filter(|p| p.native.is_none()))
    .map(|p| p.create(&context))
    .collect();
sources.sort_by_key(|s| (kind_order(s.info().kind), s.info().id));   // system first, manual last

Notice that Flatpak, Homebrew, npm and the rest are created on every distribution. Each one decides for itself, in probe(), whether it is present. A distribution only influences which native source is used. Sources are shared (Arc) so the scan can hand all of them to each source's ScanContext.

Adding a provider: one file

PROVIDERS is generated. crates/platform/linux/build.rs lists the files in crates/platform/linux/src/sources/, declares each as a module and adds its PROVIDER to the list. The file defines PROVIDER with one line, register!(<Type>);. So a new provider is a new file with two impls, that line and nothing else:

// crates/platform/linux/src/sources/homebrew.rs
pub struct HomebrewSource;

impl LinuxSource for HomebrewSource {                 // how it is created (and, for natives, which distros it serves)
    fn create(_: &Context<'_>) -> Self { Self }
}
register!(HomebrewSource);                                // defines PROVIDER, which the build script lists

impl Source for HomebrewSource {                      // what it does
    fn info(&self) -> SourceInfo { SourceInfo::new("homebrew", "Homebrew", SourceKind::Universal) }
    fn probe(&self, host: &Host) -> Availability { /* is there a brew? */ }
    fn inventory(&self, host: &Host, _: &ScanContext) -> Result<Vec<Package>, SourceError> { /* Cellar, Caskroom */ }
}

The build script never reads the files' contents. A file that forgets register! fails to compile: the generated list names homebrew::PROVIDER, which does not exist, and the comment next to it says to add register!(<Type>);. Sources never import from each other; code two sources share lives in a module outside sources/, such as files.rs or python.rs (decision D20).

7. Adding abilities later without touching existing sources

Sources read, and since Phase 3 they also plan removals; nothing changes the system before Phase 4. Abilities are added as separate traits that a source offers as an optional component:

trait Source {
    // … info, probe, inventory as today …
    fn owner_lookup(&self) -> Option<&dyn OwnerLookup>   { None }  // today: dpkg, rpm, pacman name the package that owns a file
    fn file_list(&self)    -> Option<&dyn FileList>      { None }  // today: package managers, pip, cargo
    fn dependant_lookup(&self) -> Option<&dyn Dependants> { None } // today: package managers, Flatpak, Snap
    fn remover(&self)      -> Option<&dyn Remover>       { None }  // today: a removal plan (D31); Phase 4 runs it
    fn file_installer(&self) -> Option<&dyn FileInstaller> { None } // Phase 5: install a downloaded file
    fn updater(&self)      -> Option<&dyn Updater>       { None }  // Phase 7
}
  • The default is "I can't", so adding an ability does not break the sources that don't implement it. owner_lookup(), file_list(), dependant_lookup() and remover() were added this way: only the sources that know the answer implement them, and a native source takes its remover() from the distribution's package tool (apt, dnf…).
  • The app asks "can this source remove things?" by checking for Some. The answer is honest instead of a fake method that throws.
  • An AppImage source offers remover() (trash the file and the launchers that start it) without offering updater().

8. Supporting a distribution that isn't supported today

There are three cases. Most new distributions are the first or second.

CaseExampleWork
A. A relative of a known familyLinux Mint, Pop!_OS, Rocky, Manjaro, CachyOS, a new Ubuntu flavourUsually nothing: ID_LIKE in /etc/os-release already says "debian", "fedora" or "arch". At most, one ID added to the native source's list.
B. A new native package managerAlpine (apk), Void (xbps), Gentoo (portage), Solus (eopkg)One new source file (worked example below). Nothing else changes.
C. A different model of the systemNixOS, GuixA new source (e.g. Nix profiles) and no "native" source: the system configuration is declarative, so it is listed, not removed.

Case A in practice

// crates/platform/linux/src/sources/dpkg.rs: the only change, if any
families: &[Family { name: "debian", distro_ids: &["debian", "ubuntu", "linuxmint", …, "my-new-flavour"] }],

Distributions that set ID_LIKE=debian (or fedora, arch, suse) are recognised with no change at all, because detection checks ID first and then each ID_LIKE entry.

Case B worked example: adding Alpine Linux

Alpine uses apk. Its installed-package database is a plain text file, /lib/apk/db/installed: one block per package, with lines like P: (name), V: (version), T: (description) and I: (installed size). The packages the user asked for are listed in /etc/apk/world. That is everything a source needs.

  1. Write the source: a new file sources/apk.rs following dpkg.rs. It declares which distributions it serves, reads the database, and answers "who owns this file?": 
    pub struct ApkSource;

impl LinuxSource for ApkSource {
    const NATIVE: Option<Native> = Some(Native {
        families: &[Family { name: "alpine", distro_ids: &["alpine", "postmarketos"] }],
        program: "apk",
    });
    fn create(_: &Context<'_>) -> Self { Self }
}
register!(ApkSource);

impl Source for ApkSource {
    fn info(&self) -> SourceInfo { SourceInfo::new("apk", "Alpine packages", SourceKind::System) }

    fn probe(&self, host: &Host) -> Availability {
        if host.exists("/lib/apk/db/installed") { Availability::Available { version: None } }
        else { Availability::unavailable("no apk database") }
    }

    fn inventory(&self, host: &Host, _: &ScanContext) -> Result<Vec<Package>, SourceError> {
        let db = host.read_to_string("/lib/apk/db/installed")?;
        let world = host.read_optional("/etc/apk/world")?.unwrap_or_default();
        parse(&db, &world)   // P:/V:/T:/I: blocks; names in `world` → Explicit, others → Dependency
    }

    fn owner_lookup(&self) -> Option<&dyn OwnerLookup> { Some(self) }
}

impl OwnerLookup for ApkSource {
    // one batched query: `apk info --who-owns <paths…>`, parse "<path> is owned by <pkg>" into path → package names
}
  2. Test it without an Alpine machine: a Fixture with a sample /lib/apk/db/installed and /etc/apk/world, and a FakeRunner answering the apk info --who-owns call.
  3. Prove it on the real thing: add alpine:latest to the CI container matrix and apk to the package formats (the packaging tool, nfpm, already builds .apk files). The Housekeeper binary is statically linked against musl, Alpine's own C library, so the same binary runs there.
What did not change: core, the CLI, lib.rs, distro.rs, and every other source. Flatpak, npm, pipx, cargo, AppImage and manual detection work on Alpine the moment the apk source exists, because they never depended on the distribution in the first place.

9. Supporting another operating system

The same shape, one level up. A new crate inside the platform folder (crates/platform/<os>/, D35) implements Platform and its own sources:

// crates/platform/macos/src/lib.rs (future)
pub struct MacPlatform { system: SystemInfo, sources: Vec<Arc<dyn Source>> }
// sources: HomebrewSource, AppBundleSource (/Applications), MacAppStoreSource,
// and the cross-platform ones (npm, pipx, uv, cargo) reused as-is from a shared crate.
// launchers(): the app bundles Launchpad shows; command_dirs(): the PATH (the default).

// crates/platform/src/lib.rs: the one place that registers it
#[cfg(target_os = "macos")]
pub fn detect(host: &Host) -> Result<Box<dyn Platform>, Unsupported> {
    Ok(Box::new(housekeeper_macos::MacPlatform::detect(host)))
}
// the fallback that returns Unsupported becomes #[cfg(not(any(target_os = "linux", target_os = "macos")))],
// and crates/platform/Cargo.toml gets, under [target.'cfg(target_os = "macos")'.dependencies]:
// housekeeper-macos.workspace = true; the root Cargo.toml lists "crates/platform/macos" as a member

The front ends do not change: they already call housekeeper_platform::detect. Core needs no changes either: it builds on any operating system (Unix-only checks sit behind cfg(unix)), reports SystemInfo.os as a plain string and treats every source the same way. The language-tool sources (npm, pipx, uv, cargo) read their own metadata files, so moving them into a shared crate is the one refactor this step would need.

10. Why this makes testing easy

Fake file system

Fixture creates a throwaway directory and a Host rooted there. /var/lib/pacman/local/… written by a test is what the pacman source reads.

Recorded commands

FakeRunner answers exact command lines with recorded output, and fails the test on any command it did not expect.

Real distributions in CI

Every pull request installs the package on Debian, Ubuntu, Fedora, AlmaLinux, openSUSE, Arch (x86_64 and aarch64) and checks the Silverblue image, then reads each real package database.

So a contributor can add a source for a distribution they don't run: unit tests use sample files, and CI runs it on the real system.

11. Honest limits

Resolved: the native package manager used to appear in four places (its source, a Family enum, a NativeManager enum, and three match arms). Now each native source declares its distributions and answers "who owns this file?" itself (OwnerLookup), and the build script registers every source, so adding a distribution or any other provider is one file.

The price is a small build script (crates/platform/linux/build.rs) that turns each file in src/sources/ into a module, and one register!(<Type>); line per source. File names there must be valid Rust identifiers; the build stops with a clear message otherwise.

Other deliberate limits:

  • Sources are compiled in, not loaded as plugins. A new source means a new release. This keeps the privileged parts (Phase 4) auditable. Script-installed tools are described by recipes (crates/platform/linux/recipes/*.toml, D26, D34): data files compiled in the same way, so adding one is a reviewed TOML file and no Rust, but still a release.
  • One native source per system (decision D2). A stray rpm on Ubuntu is ignored on purpose, so its empty database never shows up as a second "system".
